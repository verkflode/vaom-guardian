# VAOM Guardian

A reference implementation of the [Verkflöde Agent Operating Model (VAOM)](https://vaom.ai/) as an [OWASP Agent Control Standard](https://github.com/genai-security-project/agent-control-standard) Guardian: it fails closed, enforces a VAOM Delegation Authority Matrix, and produces evidence that the boundaries hold.

**What it is:** a reference implementation, an evidence generator, and a contributor to ACS conformance work.

**What it isn't:** a production security product, an enterprise platform, or an approval app. A Guardian `deny` is a policy-strength control; the project's reports say so, and push towards boundaries that don't depend on it.

## Check a matrix

Requires Node 22.18 or later and pnpm. Clone this repository, run `pnpm install`, then point the Guardian at a folder holding a matrix, its binding, its scoring policies and a `guardian.config.json` that names them (the Delegation Lab's export is such a folder):

```sh
node packages/guardian/src/cli.ts verify --config path/to/guardian.config.json
```

It checks the configuration the way the Guardian does before it starts (the matrix lints, and the matrix, binding and scoring policies compile together), then re-checks whatever evidence the Guardian has stored; a fresh folder has none. Any problem exits non-zero. `serve` runs the Guardian itself; see [Status](#status).

## ACS version and failure posture

- **Pinned spec:** ACS repository tag [`v0.1.2`](https://github.com/GenAI-Security-Project/agent-control-standard/tree/v0.1.2) (commit `7743826b2ec0`), whose specification text is version 0.1.0. The Guardian sends `acs_version: "0.1.0"` and accepts 0.1.x only (any patch release; a different minor version is refused, see ACS issue #196).
- **Fails closed, unlike the ACS default.** ACS defaults `on_decision_failure` to `proceed` (fail-open, §6.4). This Guardian declares `on_decision_failure: "deny"` in its handshake, and its Claude Code shim refuses to start a session unguarded when the handshake gets no answer (§4.1, whose default is also `proceed`). The Guardian alone can't guarantee this, and for Claude Code we measured why ([experiment](experiments/claude-code-hook-failures/)): Claude Code obeys an explicit `deny` in every permission mode, but treats any hook *failure* (crash, timeout, missing command, bad output) as no opinion and continues with its normal permission flow. So the shim answers explicitly on every path it can observe, the Guardian is meant to be the only source of pre-approval (no allow-rules for governed tools, so a Guardian that can't run degrades to Claude Code's own prompt), and the shim denies every call under `bypassPermissions`. The settings the shim prints also set `disableBypassPermissionsMode`, which [we measured](experiments/claude-code-shim/) makes Claude Code refuse bypass mode, so a shim that can't run degrades to Claude Code's own prompt even when bypass is requested. The remaining gap: if those settings are removed or overridden and the shim can't run while bypass is on, calls execute unguarded. Put the settings where the agent's project can't override them (managed or user settings).
- **Out of v0.1 scope, against ACS-Core.** The Guardian declares the `acs-core` profile, as every ACS deployment does, and ACS conformance is self-declared. Two items on the pinned Core list ([`conformance.md`](https://github.com/GenAI-Security-Project/agent-control-standard/blob/v0.1.2/docs/spec/conformance.md)) aren't met:
  - **`modify` is never returned.** The Guardian answers `allow`, `ask`, `deny` or `defer`, and never narrows a call's arguments. A call that would need narrowing to fit its row is placed as it stands, at the band its arguments put it in, so the result is never wider than the matrix allows. Attenuation as a narrowing-only `modify` (with the disjoint `parameter_overrides` and `redactions` of §6.3) is planned for a later version. The Claude Code shim already treats a `modify` it can't apply as deny.
  - **Wrapped MCP (`protocols/MCP/*`) isn't evaluated.** Those methods get method-not-found, never a default allow. On Claude Code, MCP tool calls arrive as ordinary `toolCallRequest`s through the shim, so they're decided anyway.

  The conformance text doesn't say whether a Guardian must emit all five dispositions or only carry them correctly; we read it strictly here and list the gap.
- **Out of v0.1 scope, against the matrix.** Consent rights (a row's `requiredApprovals`: a works council, a committee, four eyes) must exist as approval records before execution. v0.1 has no way to carry or check them, so the linter refuses a matrix that declares one rather than run it with the right ignored.

## Status

Early. Available so far:

- `schema/`: JSON Schemas for the Delegation Authority Matrix (`vaom.matrix/0.1`, frozen; `0.2`, draft) for binding an agent host's tools to matrix capabilities (`vaom.binding/0.1`, draft), for scoring policies (`vaom.scoring/0.1`, draft), for seeded cases (`vaom.seeds/0.1`, draft), and for boundary probes and their results (`vaom.probes/0.1`, `vaom.probe-result/0.1`, drafts), with examples and tests. (The frozen 0.1 schema's own description still reads "Draft 0.1, a sketch": that text was frozen with it.)

- `packages/core`: the pure core (no I/O, no eval, zero runtime dependencies, runs in Node and the browser). So far it holds the **linter**, `lintMatrix`, `lintBinding` and `lintScoring`: JSON Schema validation through validators compiled ahead of time, plus the rules JSON Schema can't express, such as reference integrity, uniqueness (rows, capabilities, cap, restriction and breaker ids), currency consistency (including a binding that fixes a currency its row limits in another), positive durations (a zero window would switch a cap or signal off), lease lifetimes, sub-agent authority, funded review load, and the binding checked against its matrix. It fails closed: an unknown format or a schema failure is never accepted.

It also holds the **evaluator**, `compilePolicy` and `evaluate`: it places one tool call in a band from a lint-clean matrix, binding and scoring policies. The matrix grants nothing outside its effective window (`effective.from` and `until`), so the evaluator needs the call's time, and without a valid one nothing is placed. Ceilings, caps, restrictions and missing verification only ever narrow; batch items count toward caps together; and anything it can't place is `unplaceable`, never allowed. It returns the cap uses to reserve, for the cap store that comes next.

**Confidence scores are computed, not supplied.** A matrix row cites a scoring policy by id and version, a third human-approved file next to the matrix and binding, holding the structure of VAOM v5 §8: must-pass gates, per-dimension floors and weights. The core computes each dimension deterministically: data completeness and rule match from the facts the binding extracts, anomaly signals (an unfamiliar counterparty, an unusual amount, a burst) from the Guardian's own decision history. Only executed decisions make a counterparty familiar or an amount usual, so an agent can't build that history by asking, while every attempt counts towards a burst. A failed gate sets the level to low; a breached floor or a failed hard rule caps it at medium. The agent's stated certainty carries no weight: it can only lower a score or cap its level. A matrix citing a policy that isn't loaded, or a policy reading a fact the binding doesn't extract, doesn't compile. Independent verification needs a verifier that isn't the Guardian. The core takes a verifier's verdict as an input, but the Guardian has no verifier channel yet, so in a running Guardian rows that require verification stop at Band B. Calibration (deriving thresholds from labelled outcomes) happens offline; the matrix records its target and sample.

And it holds **decision records** (`vaom.decision/0.4`, schema in `schema/vaom-decision-0.4.schema.json`): each decision as replayable evidence (matrix, binding and scoring policy versions, outcome, band, approver, reasons, each placement's score dimension by dimension, cap reservations, and later its resolution). Scores name the checks, rules and signals that failed or fired, never the values they read. Records in the earlier `0.3` format still validate, for older evidence. Arguments are stored only as a digest; facts are recorded in clear, as a keyed digest, or not at all, as the binding says. A record that can't be built means no action.

The **cap ledger** and **`decide`** complete the decision path: `decide` evaluates a call against the ledger, builds its record and reserves its cap uses in one synchronous step, so parallel calls can't each see room under a cap only one of them fits in. Pending approvals count as used until resolved; rejected, expired and withdrawn ones are released. Until its history is loaded the ledger refuses to reserve, so no decision is made against unknown usage. A ledger rebuilt from decision records matches the live one exactly.

**Execution contexts and leases** bound authority in time. A call has authority only inside a live context covering its row; a context bound to a task covers only calls naming that task. Contexts expire, can't be reused, and revocation cascades. Sub-agent contexts can only narrow: fewer rows, stricter band ceilings, earlier expiry, within the matrix's depth and fan-out, and a spawn outside the allowed patterns needs escalation. When a context covers several rows that each define sub-agent patterns, every one of them must allow the spawn, and the strictest depth, fan-out, count and lifetime apply. A record names the context that actually authorised its call. Leases give continuous agents short, renewable observation authority; acting needs a per-alert response context; a failed health check withdraws response authority at once; and at the maximum lifetime without human re-attestation the lease degrades to observe-only, never extends.

**The Delegation Scorecard** (VAOM v5 §11), `scorecard`, is computed from decision records, per decision type. Of the thirteen metrics it measures what the records support: band distribution against the volumes expected at design, exception-path share, dimension correlation with the composite (Dimension Collapse), verifier disagreement, oversight load against funded reviewer hours, review engagement (approval share and review time), escalation outcomes, and scope denials per agent. With seed outcomes it also gives the seeded-error detection rate against the row's target; with probe results, boundary verification; and with spawn events, chain integrity (any spawn past the matrix's depth, fan-out or counts, or of a type no pattern allows, is a breach even though the Guardian denied it: the attempt is the signal). The rest are reported as not measured, with the reason: Band A error rate needs post-execution audit outcomes; and the Guardian doesn't see retrievals, so it can't measure stale knowledge. Below a minimum sample, and where the matrix declares no healthy range, it reports values without a verdict (oversight load needs at least a week of records; chain integrity needs a spawn); the paper's illustrative defaults apply only where the matrix is silent, and are named as such. Each record counts once by id, and the report says how many duplicates and undatable records it set aside. Review metrics are aggregated per row and its reviewer role, never per named reviewer. A role held by one person is that person, though: there the review figures describe them, so know who holds a role before publishing a scorecard.

**Boundary verification** (VAOM v5 §9, metric 13): `assessBoundaries` judges each boundary the matrix relies on from probe results. A boundary is verified when its latest conclusive probe, within its schedule, showed it holding by the mechanism the matrix claims (absent, scope-denied, or policy). It is degraded when it held only by a weaker mechanism (an "absent" tool that turns up in the agent's manifest, even if the Guardian then denied the call), failed when the probe crossed it, and overdue or unverified otherwise; anything but verified counts at policy strength, and a failure names the dependent rows and the matrix's circuit breakers. `classify` turns what a probe saw into that verdict, so every runner applies the same rules: reaching the canary is a crossing; a run that saw no tool manifest is inconclusive, never absent; and a call that ran and failed proves a target's refusal only if the error matches the probe's refusal pattern. A result whose claim its own evidence contradicts (claimed absent with the canary hit, say) is refused at import and never credited; only the manifest, stored as a digest, can't be re-checked.

**VAOM v5's worked examples run end to end** (`packages/core/test/worked-examples.test.ts`): 7B AML triage, 7D autonomous incident remediation and 7E delegated purchasing, each with its own matrix, binding and scoring policies in `schema/examples/`. Every case quotes the whitepaper sentence it checks. Figures the paper doesn't state are illustrative in the examples, which say so; the paper's composites are its own policies' outputs, so the tests check the bands they lead to, not the numbers. These double as candidate conformance vectors for ACS.

- `packages/acs`: the **ACS wire adapter**, also pure (it imports only the core). It handles the handshake (declaring `on_decision_failure: "deny"`, HMAC-SHA256 only, human approvers only), per-session HMAC keys derived with HKDF, envelope signatures, replay protection (request ids and nonces, with a skew window), and the hash-chained audit trail that the `acs-audit` profile asks for. It translates between ACS steps and the core: `toolCallRequest` goes through `decide`; review and escalation become `ask`, with a deny on timeout; non-delegable becomes `deny`; unplaceable becomes `defer`, with a deny on timeout; `sessionStart` opens the execution context set by configuration; `subagentStart` derives an attenuated context; `toolCallResult` resolves the decision record. Requests are checked in a fixed order: envelope schema, version, signature, replay, session, payload, chain. Every failure is an error or a deny; methods it doesn't evaluate (wrapped protocols, memory and skill steps) are errors, never a default allow. A result showing that an `ask` executed without its approval is reported as an incident, and its output is withheld. Reasons go on the wire as codes only, never argument values. ACS v0.1 doesn't yet fix the HKDF parameters (ACS issues #118 and #11), so ours are provisional and stated in `src/hkdf.ts`. The vendored ACS schemas are in `packages/acs/vendor/acs-v0.1.2/`, unmodified, under their Apache-2.0 licence.

- `packages/guardian`: the **Guardian process**. It uses Node built-ins only, listens on 127.0.0.1, and never makes outbound connections (a source scan enforces this).
  - **Persistence:** it serves the ACS endpoint and saves every decision record, chain entry and event to append-only JSONL files, synced to disk before it answers. If saving fails, the agent gets an error, which means deny.
  - **Approvals:** reviews and escalations wait on a local approval page. Approving takes a WebAuthn assertion with user verification (Touch ID) from a credential enrolled for the approver role the decision names. The challenge commits to that one decision and its argument digest. Rejecting needs no credential. An ask past its timeout expires, which means deny. Records and approval events name the role, not the person, unless the matrix enables reviewer-level metrics (which requires a recorded approval such as a DPIA). The approval event still keeps the credential id, because `verify` needs it to check the signature, so the event log links approvals to an enrolled passkey and should be handled as personal data. A call's arguments are held in memory only while its ask is pending, and a decided ask is forgotten one approval timeout later.
  - **Enrollment** takes a one-time link printed on the Guardian's terminal. Attestation isn't checked, because platform passkeys mostly send none. `vaom-guardian credentials --config <guardian.json>` lists enrolled credentials; `vaom-guardian revoke --config <guardian.json> <id>` revokes one, and a running Guardian refuses it from its next approval.
  - **Restart:** asks left pending by an unclean stop expire on restart, and a damaged history stops it from starting; a write torn by the crash, never acknowledged, is cut off before the next one. Requests signed before the Guardian started are refused, so nothing from before a restart can be replayed, and agents start new sessions. A call approved just before an unclean stop may or may not have run: its record stays open and its cap use counted, and `verify` lists it.
  - **Seeded cases** (VAOM v5 Readiness Condition 6): with a seed set configured, the Guardian plants known-error asks beside real reviews, at the rate the matrix row sets, and only on rows that enable seeding (which the matrix allows only where records feed no regulatory reporting, investigations or decisions about people). A seed is placed by the real evaluator, without reserving anything, so the page shows exactly what a real ask would. It never becomes a decision record, and it never reaches the agent, a cap, the decision history or a calibration sample. Approving one is a miss, rejecting one a detection; either way nothing executes, and the page reveals the known error only after the decision. The page tells reviewers that seeding exists and at what rate, never which asks are seeds. A seed follows a real ask after a random delay of minutes, and goes in only while a real ask is still waiting, so its timing gives as little away as it can. Outcomes are seed events, aggregated per row for the scorecard; `verify` checks approved seeds' Touch ID assertions and that no seed ever became a decision record. **Strength:** an agent on the same machine that reads the approval page could tell seeds apart from its own asks (their request ids never came from it). That doesn't let it approve anything, but seeding measures reviewers against agents that don't do this.
  - **Spawns:** every sub-agent spawn decision, allowed or denied, is stored as a spawn event with its reason, as the evidence for chain integrity.
  - **Probe results:** `vaom-guardian probe import --config <guardian.json> result.json...` checks each result against its schema and the matrix and appends it to the store, all or nothing. A result is the runner's claim, kept as evidence; `verify` re-checks it, and the scorecard judges the boundaries from it.
  - **Scorecard:** `vaom-guardian scorecard --config <guardian.json> [--from ISO] [--to ISO] [--json]` reads the evidence files (no Guardian needs to run) and prints the scorecard for a period, by default the last seven days.
  - **Verification:** `vaom-guardian verify` first checks the configuration as `serve` would, and refuses to go on if the Guardian wouldn't start with it. Then it re-checks the evidence offline: record schemas, and that each record's decision is the one its placements combine to; every session's hash chain, and that each record's chain entry is in it; every approval's signature against the enrolled key with its challenge recomputed, that its decision has a record, and that its credential wasn't revoked before it; and that every executed review or escalation has an approval for the same decision and role. It lists decisions never resolved as open items. What it can't see: chain entries cut off after a session's last decision (observed steps have no record to cross-check), and a deleted rejection or expiry, which leaves its decision looking open.

  Try it: `node packages/guardian/src/cli.ts serve --config packages/guardian/examples/incident.guardian.json --enroll owner:sre-lead`, open the printed link to enroll, run `node packages/guardian/examples/demo-agent.ts`, and approve at `http://localhost:47100/`.

  **Strength:** an agent running as the same OS user as the Guardian can read its data directory, including the shared secret, and could stop the Guardian or re-enroll. It can't produce a Touch ID assertion, and most of what it could do to the files shows up in `verify` (see above for what doesn't), but this is policy strength, not isolation. Running the Guardian as a separate user is the stronger setup.

- `packages/probe`: **boundary probes on Claude Code**. `vaom-probe run --probes <probes.json> --matrix <matrix.json> --project <agent project>` runs each probe's attempt as a real `claude -p` session in the agent's own project, so its hooks and MCP servers are the ones under test, and writes a `vaom.probe-result` per boundary. It reads the tool manifest, the calls, the denials and the target's refusals from the stream-json transcript, matching each denial to its call by id. A denial counts as the Guardian holding only when the call's result carries the shim's `VAOM Guardian:` reason: Claude Code lists its own refusals in the same place, and those aren't the Guardian. So that Claude Code doesn't refuse a probed tool just because nobody granted it, the runner grants the probe's forbidden tools for the session (`--allowedTools`); hooks and deny rules still win over a grant, and `--no-grant` turns it off. It learns that a canary was reached from a Unix socket it names in `VAOM_CANARY_SOCKET`, which canary targets write to. It keeps the hits in memory, so the agent under test, running as the same user, can fake a hit (which fails closed) but can't erase one. It keeps only digests of the transcript unless asked (`--keep-transcripts`). It loads project settings by default; `--setting-sources` must match where the deployment under test keeps its hooks, or no hook fires and every boundary reads crossed. An "absent" verdict rests on the session's initial tool manifest, which we measured to list MCP tools even when their schemas load later (Claude Code 2.1.296); the result carries the host version it was measured on. A timed-out session is stopped with its whole process group. Unlike the shim and the Guardian, it starts processes, because the agent host is what it probes. Probes attempt forbidden actions: point them at canaries, never live systems. A run under a real Claude Code is in [`experiments/boundary-probes/`](experiments/boundary-probes/).

- `packages/claude-code`: the **Claude Code shim**, a hook process that Claude Code starts once per hook call. It speaks ACS to the Guardian on 127.0.0.1 and nothing else (a source scan enforces this).
  - **Decisions:** `PreToolUse` becomes a signed `toolCallRequest`, and the Guardian's answer counts only if its signature verifies under the session key. An `allow` becomes allow. An `ask` holds the call while the Guardian's approval page collects a decision, and the shim acts only on a signed approval status. `deny`, `defer` and everything else become deny.
  - **Failure:** the shim always answers explicitly. A Guardian that's down, slow, or answers wrongly, a session it can't negotiate (ACS §4.1's startup posture, which we set to `refuse`, not the default `proceed`), an ask without an approval by the shim's deadline, hook input that names no hook event, and `bypassPermissions` all get a deny. While a hook holds its session's state lock it keeps the lock fresh, so a slow Guardian can't make another hook take it. It answers before Claude Code's own hook timeout could turn silence into "no opinion".
  - **Execution:** `PostToolUse` and `PostToolUseFailure` report the execution against the decision it ran under, matched by `tool_use_id`. A call that ran with no decision on record is reported anyway: that's the trace a failed `PreToolUse` hook leaves. The Guardian logs it as an incident, and the shim withholds the output from the model.
  - **Sessions:** each Claude Code session is its own ACS session, with the chain head claimed on every request (§8.6). Parallel tool calls are serialized per session for each round trip, never while a human decides. After a Guardian restart or a chain mismatch, the shim negotiates a new session.
  - **Host-internal tools:** Claude Code's `ToolSearch` only loads a tool's schema, so the shim allows it without asking the Guardian. The tool it loads still needs its own decision.

  Set it up: `node packages/claude-code/src/cli.ts settings --guardian <guardian.json> --agent <agent id>` prints the hooks for Claude Code's settings, routing every tool through the shim and disabling bypass mode. Keep allow-rules for governed tools out of your settings: the Guardian's `allow` should be the only pre-approval. A run under a real Claude Code is in [`experiments/claude-code-shim/`](experiments/claude-code-shim/).

  - **Sub-agents:** a call to Claude Code's `Agent` tool is a spawn, decided as ACS `subagentStart`. The Guardian derives an attenuated context for that sub-agent type, or denies the spawn. The sub-agent then speaks on its own ACS session as `{agent}/{type}`, so every call it makes is decided under the derived context. When it stops, its session ends and its context closes, freeing its place in the parent's fan-out. A sub-agent Claude Code starts without an allowed spawn has no session, and every call it makes is denied. Claude Code doesn't link `SubagentStart` to the `Agent` call that caused it. So two spawns of the same type in flight at once may be matched to each other's sub-agent. Both were allowed the same pattern under the same parent, so this changes which spawn the evidence links a sub-agent to, never what it may do.

## Development

Requires Node 22.18+ (the CLIs run as TypeScript directly) and pnpm. `pnpm install`, then `pnpm test` (package tests and schema tests) and `pnpm typecheck`. After changing a schema, run `pnpm gen:validators`; a test fails if the committed validators are stale.
