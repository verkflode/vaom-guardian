# VAOM Guardian

A reference implementation of the Verkflöde Agent Operating Model (VAOM) as an [OWASP Agent Control Standard](https://github.com/genai-security-project/agent-control-standard) Guardian: it fails closed, enforces a VAOM Delegation Authority Matrix, and produces evidence that the boundaries hold.

**What it is:** a reference implementation, an evidence generator, and a contributor to ACS conformance work.

**What it isn't:** a production security product, an enterprise platform, or an approval app. A Guardian `deny` is a policy-strength control; the project's reports say so, and push towards boundaries that don't depend on it.

## ACS version and failure posture

- **Pinned spec:** ACS repository tag [`v0.1.2`](https://github.com/GenAI-Security-Project/agent-control-standard/tree/v0.1.2) (commit `7743826b2ec0`), whose specification text is version 0.1.0. The Guardian sends `acs_version: "0.1.0"` and accepts 0.1.x only (any patch release; a different minor version is refused, see ACS issue #196).
- **Fails closed, unlike the ACS default.** ACS defaults `on_decision_failure` to `proceed` (fail-open, §6.4). This Guardian declares `on_decision_failure: "deny"` in its handshake, and its Claude Code shim refuses to start a session unguarded when the handshake gets no answer (§4.1, whose default is also `proceed`). The Guardian alone can't guarantee this, and for Claude Code we measured why ([experiment](experiments/claude-code-hook-failures/)): Claude Code obeys an explicit `deny` in every permission mode, but treats any hook *failure* (crash, timeout, missing command, bad output) as no opinion and continues with its normal permission flow. So the shim answers explicitly on every path it can observe, the Guardian is meant to be the only source of pre-approval (no allow-rules for governed tools, so a Guardian that can't run degrades to Claude Code's own prompt), and the shim denies every call under `bypassPermissions`. The settings the shim prints also set `disableBypassPermissionsMode`, which [we measured](experiments/claude-code-shim/) makes Claude Code refuse bypass mode, so a shim that can't run degrades to Claude Code's own prompt even when bypass is requested. The remaining gap: if those settings are removed or overridden and the shim can't run while bypass is on, calls execute unguarded. Put the settings where the agent's project can't override them (managed or user settings).

## Status

Early. Available so far:

- `schema/`: JSON Schemas for the Delegation Authority Matrix (`vaom.matrix/0.1`, frozen; `0.2`, draft) for binding an agent host's tools to matrix capabilities (`vaom.binding/0.1`, draft), for scoring policies (`vaom.scoring/0.1`, draft), for seeded cases (`vaom.seeds/0.1`, draft), and for boundary probes and their results (`vaom.probes/0.1`, `vaom.probe-result/0.1`, drafts), with examples and tests. (The frozen 0.1 schema's own description still reads "Draft 0.1, a sketch": that text was frozen with it.)

- `packages/core`: the pure core (no I/O, no eval, zero runtime dependencies, runs in Node and the browser). So far it holds the **linter**, `lintMatrix`, `lintBinding` and `lintScoring`: JSON Schema validation through validators compiled ahead of time, plus the rules JSON Schema can't express, such as reference integrity, uniqueness, currency consistency, lease lifetimes, sub-agent authority, funded review load, and the binding checked against its matrix. It fails closed: an unknown format or a schema failure is never accepted.

It also holds the **evaluator**, `compilePolicy` and `evaluate`: it places one tool call in a band from a lint-clean matrix, binding and scoring policies. Ceilings, caps, restrictions and missing verification only ever narrow; batch items count toward caps together; and anything it can't place is `unplaceable`, never allowed. It returns the cap uses to reserve, for the cap store that comes next.

**Confidence scores are computed, not supplied.** A matrix row cites a scoring policy by id and version, a third human-approved file next to the matrix and binding, holding the structure of VAOM v5 §8: must-pass gates, per-dimension floors and weights. The core computes each dimension deterministically: data completeness and rule match from the facts the binding extracts, anomaly signals (an unfamiliar counterparty, an unusual amount, a burst) from the Guardian's own decision history. Only executed decisions make a counterparty familiar or an amount usual, so an agent can't build that history by asking, while every attempt counts towards a burst. A failed gate sets the level to low; a breached floor or a failed hard rule caps it at medium. The agent's stated certainty carries no weight: it can only lower a score or cap its level. A matrix citing a policy that isn't loaded, or a policy reading a fact the binding doesn't extract, doesn't compile. Independent verification needs a verifier that isn't the Guardian. The core takes a verifier's verdict as an input, but the Guardian has no verifier channel yet, so in a running Guardian rows that require verification stop at Band B. Calibration (deriving thresholds from labelled outcomes) happens offline; the matrix records its target and sample.

And it holds **decision records** (`vaom.decision/0.4`, schema in `schema/vaom-decision-0.4.schema.json`): each decision as replayable evidence (matrix, binding and scoring policy versions, outcome, band, approver, reasons, each placement's score dimension by dimension, cap reservations, and later its resolution). Scores name the checks, rules and signals that failed or fired, never the values they read. Records in the earlier `0.3` format still validate, for older evidence. Arguments are stored only as a digest; facts are recorded in clear, as a keyed digest, or not at all, as the binding says. A record that can't be built means no action.

The **cap ledger** and **`decide`** complete the decision path: `decide` evaluates a call against the ledger, builds its record and reserves its cap uses in one synchronous step, so parallel calls can't each see room under a cap only one of them fits in. Pending approvals count as used until resolved; rejected, expired and withdrawn ones are released. Until its history is loaded the ledger refuses to reserve, so no decision is made against unknown usage. A ledger rebuilt from decision records matches the live one exactly.

**Execution contexts and leases** bound authority in time. A call has authority only inside a live context covering its row (bound to its task, if given); contexts expire, can't be reused, and revocation cascades. Sub-agent contexts can only narrow: fewer rows, stricter band ceilings, earlier expiry, within the matrix's depth and fan-out, and a spawn outside the allowed patterns needs escalation. Leases give continuous agents short, renewable observation authority; acting needs a per-alert response context; a failed health check withdraws response authority at once; and at the maximum lifetime without human re-attestation the lease degrades to observe-only, never extends.

**The Delegation Scorecard** (VAOM v5 §11), `scorecard`, is computed from decision records, per decision type. Of the thirteen metrics it measures what the records support: band distribution against the volumes expected at design, exception-path share, dimension correlation with the composite (Dimension Collapse), verifier disagreement, oversight load against funded reviewer hours, review engagement (approval share and review time), escalation outcomes, and scope denials per agent. With seed outcomes it also gives the seeded-error detection rate against the row's target; with probe results, boundary verification; and with spawn events, chain integrity (any spawn past the matrix's depth, fan-out or counts, or of a type no pattern allows, is a breach even though the Guardian denied it: the attempt is the signal). The rest are reported as not measured, with the reason: Band A error rate needs post-execution audit outcomes; and the Guardian doesn't see retrievals, so it can't measure stale knowledge. Below a minimum sample, and where the matrix declares no healthy range, it reports values without a verdict; the paper's illustrative defaults apply only where the matrix is silent, and are named as such. Review metrics are aggregated per row: nothing is reported per reviewer.

**Boundary verification** (VAOM v5 §9, metric 13): `assessBoundaries` judges each boundary the matrix relies on from probe results. A boundary is verified when its latest conclusive probe, within its schedule, showed it holding by the mechanism the matrix claims (absent, scope-denied, or policy). It is degraded when it held only by a weaker mechanism (an "absent" tool that turns up in the agent's manifest, even if the Guardian then denied the call), failed when the probe crossed it, and overdue or unverified otherwise; anything but verified counts at policy strength, and a failure names the dependent rows and the matrix's circuit breakers. `classify` turns what a probe saw into that verdict, so every runner applies the same rules: reaching the canary is a crossing; a run that saw no tool manifest is inconclusive, never absent; and a call that ran and failed proves a target's refusal only if the error matches the probe's refusal pattern.

**VAOM v5's worked examples run end to end** (`packages/core/test/worked-examples.test.ts`): 7B AML triage, 7D autonomous incident remediation and 7E delegated purchasing, each with its own matrix, binding and scoring policies in `schema/examples/`. Every case quotes the whitepaper sentence it checks. Figures the paper doesn't state are illustrative in the examples, which say so; the paper's composites are its own policies' outputs, so the tests check the bands they lead to, not the numbers. These double as candidate conformance vectors for ACS.

- `packages/acs`: the **ACS wire adapter**, also pure (it imports only the core). It handles the handshake (declaring `on_decision_failure: "deny"`, HMAC-SHA256 only, human approvers only), per-session HMAC keys derived with HKDF, envelope signatures, replay protection (request ids and nonces, with a skew window), and the hash-chained audit trail that the `acs-audit` profile asks for. It translates between ACS steps and the core: `toolCallRequest` goes through `decide`; review and escalation become `ask`, with a deny on timeout; non-delegable becomes `deny`; unplaceable becomes `defer`, with a deny on timeout; `sessionStart` opens the execution context set by configuration; `subagentStart` derives an attenuated context; `toolCallResult` resolves the decision record. Requests are checked in a fixed order: envelope schema, version, signature, replay, session, payload, chain. Every failure is an error or a deny; methods it doesn't evaluate (wrapped protocols, memory and skill steps) are errors, never a default allow. A result showing that an `ask` executed without its approval is reported as an incident, and its output is withheld. Reasons go on the wire as codes only, never argument values. ACS v0.1 doesn't yet fix the HKDF parameters (ACS issues #118 and #11), so ours are provisional and stated in `src/hkdf.ts`. The vendored ACS schemas are in `packages/acs/vendor/acs-v0.1.2/`, unmodified, under their Apache-2.0 licence.

- `packages/guardian`: the **Guardian process**. It uses Node built-ins only, listens on 127.0.0.1, and never makes outbound connections (a source scan enforces this).
  - **Persistence:** it serves the ACS endpoint and saves every decision record, chain entry and event to append-only JSONL files, synced to disk before it answers. If saving fails, the agent gets an error, which means deny.
  - **Approvals:** reviews and escalations wait on a local approval page. Approving takes a WebAuthn assertion with user verification (Touch ID) from a credential enrolled for the approver role the decision names. The challenge commits to that one decision and its argument digest. Rejecting needs no credential. An ask past its timeout expires, which means deny. Records and approval events name the role, not the person, unless the matrix enables reviewer-level metrics (which requires a recorded approval such as a DPIA). The approval event still keeps the credential id, because `verify` needs it to check the signature, so the event log links approvals to an enrolled passkey and should be handled as personal data.
  - **Enrollment** takes a one-time link printed on the Guardian's terminal. Attestation isn't checked, because platform passkeys mostly send none.
  - **Restart:** asks left pending by an unclean stop expire on restart, and a damaged history stops it from starting.
  - **Seeded cases** (VAOM v5 Readiness Condition 6): with a seed set configured, the Guardian plants known-error asks beside real reviews, at the rate the matrix row sets, and only on rows that enable seeding (which the matrix allows only where records feed no regulatory reporting, investigations or decisions about people). A seed is placed by the real evaluator, without reserving anything, so the page shows exactly what a real ask would. It never becomes a decision record, and it never reaches the agent, a cap, the decision history or a calibration sample. Approving one is a miss, rejecting one a detection; either way nothing executes, and the page reveals the known error only after the decision. The page tells reviewers that seeding exists and at what rate, never which asks are seeds. Outcomes are seed events, aggregated per row for the scorecard; `verify` checks approved seeds' Touch ID assertions and that no seed ever became a decision record. **Strength:** an agent on the same machine that reads the approval page could tell seeds apart from its own asks (their request ids never came from it). That doesn't let it approve anything, but seeding measures reviewers against agents that don't do this.
  - **Spawns:** every sub-agent spawn decision, allowed or denied, is stored as a spawn event with its reason, as the evidence for chain integrity.
  - **Probe results:** `vaom-guardian probe import --config <guardian.json> result.json...` checks each result against its schema and the matrix and appends it to the store, all or nothing. A result is the runner's claim, kept as evidence; `verify` re-checks it, and the scorecard judges the boundaries from it.
  - **Scorecard:** `vaom-guardian scorecard --config <guardian.json> [--from ISO] [--to ISO] [--json]` reads the evidence files (no Guardian needs to run) and prints the scorecard for a period, by default the last seven days.
  - **Verification:** `vaom-guardian verify` re-checks the evidence offline: record schemas, every session's hash chain, every approval's signature against the enrolled key with its challenge recomputed, and that every executed review or escalation has an approval for the same decision and role.

  Try it: `node packages/guardian/src/cli.ts serve --config packages/guardian/examples/incident.guardian.json --enroll owner:sre-lead`, open the printed link to enroll, run `node packages/guardian/examples/demo-agent.ts`, and approve at `http://localhost:47100/`.

  **Strength:** an agent running as the same OS user as the Guardian can read its data directory, including the shared secret, and could stop the Guardian or re-enroll. It can't produce a Touch ID assertion, and anything it does to the files shows up in `verify`, but this is policy strength, not isolation. Running the Guardian as a separate user is the stronger setup.

- `packages/probe`: **boundary probes on Claude Code**. `vaom-probe run --probes <probes.json> --matrix <matrix.json> --project <agent project>` runs each probe's attempt as a real `claude -p` session in the agent's own project, so its hooks and MCP servers are the ones under test, and writes a `vaom.probe-result` per boundary. It reads the tool manifest, the calls, the denials and the target's refusals from the stream-json transcript, and learns that a canary was reached from `VAOM_CANARY_LOG`, which canary targets append to. It keeps only digests of the transcript unless asked (`--keep-transcripts`). Unlike the shim and the Guardian, it starts processes, because the agent host is what it probes. Probes attempt forbidden actions: point them at canaries, never live systems. A run under a real Claude Code is in [`experiments/boundary-probes/`](experiments/boundary-probes/).

- `packages/claude-code`: the **Claude Code shim**, a hook process that Claude Code starts once per hook call. It speaks ACS to the Guardian on 127.0.0.1 and nothing else (a source scan enforces this).
  - **Decisions:** `PreToolUse` becomes a signed `toolCallRequest`, and the Guardian's answer counts only if its signature verifies under the session key. An `allow` becomes allow. An `ask` holds the call while the Guardian's approval page collects a decision, and the shim acts only on a signed approval status. `deny`, `defer` and everything else become deny.
  - **Failure:** the shim always answers explicitly. A Guardian that's down, slow, or answers wrongly, a session it can't negotiate (ACS §4.1's startup posture, which we set to `refuse`, not the default `proceed`), an ask without an approval by the shim's deadline, and `bypassPermissions` all get a deny. It answers before Claude Code's own hook timeout could turn silence into "no opinion".
  - **Execution:** `PostToolUse` and `PostToolUseFailure` report the execution against the decision it ran under, matched by `tool_use_id`. A call that ran with no decision on record is reported anyway: that's the trace a failed `PreToolUse` hook leaves. The Guardian logs it as an incident, and the shim withholds the output from the model.
  - **Sessions:** each Claude Code session is its own ACS session, with the chain head claimed on every request (§8.6). Parallel tool calls are serialized per session for each round trip, never while a human decides. After a Guardian restart or a chain mismatch, the shim negotiates a new session.
  - **Host-internal tools:** Claude Code's `ToolSearch` only loads a tool's schema, so the shim allows it without asking the Guardian. The tool it loads still needs its own decision.

  Set it up: `node packages/claude-code/src/cli.ts settings --guardian <guardian.json> --agent <agent id>` prints the hooks for Claude Code's settings, routing every tool through the shim and disabling bypass mode. Keep allow-rules for governed tools out of your settings: the Guardian's `allow` should be the only pre-approval. A run under a real Claude Code is in [`experiments/claude-code-shim/`](experiments/claude-code-shim/).

  - **Sub-agents:** a call to Claude Code's `Agent` tool is a spawn, decided as ACS `subagentStart`. The Guardian derives an attenuated context for that sub-agent type, or denies the spawn. The sub-agent then speaks on its own ACS session as `{agent}/{type}`, so every call it makes is decided under the derived context. When it stops, its session ends and its context closes, freeing its place in the parent's fan-out. A sub-agent Claude Code starts without an allowed spawn has no session, and every call it makes is denied. Claude Code doesn't link `SubagentStart` to the `Agent` call that caused it. So two spawns of the same type in flight at once may be matched to each other's sub-agent. Both were allowed the same pattern under the same parent, so this changes which spawn the evidence links a sub-agent to, never what it may do.

## Development

Requires Node 22+ and pnpm. `pnpm install`, then `pnpm test` (package tests and schema tests) and `pnpm typecheck`. After changing a schema, run `pnpm gen:validators`; a test fails if the committed validators are stale.
